## 结论

这个项目走的是“Godot 前端 + 本地 Kotlin 网关 + 原版 Unciv `core`”路线，规则和 AI 没有重写。从这个方向看，进展是扎实的：本地通信协议、玩家快照和命令校验体系已经跑通，城市、宗教、外交、城邦、伟人、投票这几个领域也接了不少命令。

但离“完整复刻 Unciv”还差很多。一是界面仍是验证用的原型，大部分操作靠下拉框和按钮完成，地图只有简单几何图形；二是单位玩法只做了非登船的陆军；三是科技树、政策树、间谍、交易谈判、各种事件、Mod、多人游戏都还没做。而且任何一个没接入的弹窗事件都会卡住“结束回合”，只能提示玩家存档后回原版客户端处理，这是正常游玩一局时最大的障碍。

我在这台机器上跑了内核测试 `:godot-kernel:test`，260 项全部通过。Godot 界面我没法运行：这里是 Linux 云环境，你指定的 Godot 在 Windows 路径下。所以界面部分的判断来自读代码和 `tests/smoke.gd`，没有做界面实测。

## 可以优化的地方

**1. 先解决“事件卡死回合”（最高优先级）**

现在只要遇到没接入的弹窗，这局就没法在 Godot 里继续。建议加一个通用的“事件选择”通道：内核把原版 `AlertPopup` 或事件的选项列表转成通用的“选项 + 可用状态 + 原因”数据，前端用一个统一的对话框显示。这样新弹窗类型只需要写内核适配，不需要每种都写一套界面。

**2. 网关命令改成注册表**

同一个命令名在 `GameSession.kt` 里要手写三遍：准备阶段（78–101 行）、执行阶段（140–146 行）、`inPlaceCommands` 列表（303–310 行）。每加一个命令就要改三处，漏掉一处就是隐蔽 bug。建议定义一个统一接口，每个命令声明自己是否会修改状态、校验逻辑和执行逻辑，由 `GameSession` 按注册表分发。

**3. 拆分 `main.gd`**

外交、宗教、伟人、投票、资产处置、经济这六个领域，各自复制了一套“代际计数、状态戳、事务锁、结果不确定、确认框”的相同模式。`execute()` 已经有 6 个布尔参数，`_on_busy()` 第 1821 行一行要检查 13 个条件。建议：
- 把事务、确认、恢复逻辑抽成一个可复用的“事务控制器”；
- 每个领域做成独立的 `.tscn` 面板场景加脚本；
- `main.gd` 只负责布局和路由。

不做这一步，后面再加科技树、交易这些界面，复杂度会急剧上升。

**4. 快照和渲染的性能**

- 目前每条命令都返回完整快照（所有地块），地图也整张重绘。小地图没问题，大地图会明显变慢。可以按方案里的思路加增量更新：返回变化的地块、单位、城市，或者给地块数据加版本号只发变化部分。
- 地形改用 `TileMapLayer` 批量绘制，只有交互覆盖层用 `_draw`。
- 贴图改为导入的图集，不要运行时读取 `../android` 下的文件。

**5. 下一回合改成异步**

AI 回合现在是一次同步 HTTP 请求，前端超时 120 秒。游戏后期可能超时，也没有进度显示。建议改成“提交任务，然后轮询或通过 WebSocket 接收进度和表现事件”。这样也能顺便产出方案里说的动画事件流，给移动和战斗动画用。

**6. 界面向原版交互靠拢**

- 科研和政策从下拉框改成树状界面，内核补充花费、剩余回合、前置科技等数据。
- 城市标签改成原版风格的横幅。
- 按文明颜色画领土边界。
- 加一个通知列表，点击能定位到地图位置。
- 右键直接移动或攻击，不再需要先预览再点“确认”。二次确认只留给焚城、宣战这类高风险操作。

**7. 翻译**

让内核在快照里附带翻译好的名称，或者提供一个翻译查询接口，复用原版的中文翻译文件，不要在 Godot 里另建一套。

**8. 测试**

- 验证开局关掉了蛮族、城邦和遗迹，覆盖面偏窄。可以再加一个标准配置的长局回归测试。
- 用你的真实历史存档做回归，这项在历史记录里一直标着“待验”。
- `smoke.gd` 已经 3596 行，建议按领域拆开，和上面的界面拆分同步进行。

## 下一步任务具体方案（第 1 优先：通用事件与弹窗通道）

### 目标

让任何未接入的弹窗（首先是 `AlertType.Event` 触发式多选事件）都能在 Godot 内完成处置，不再卡死“结束回合”；并严格复刻原生 `RenderEvent` 的解析/触发语义，不改 `core`。这是让“正常玩一局”能一直玩下去的头号前提。

### 原生语义参照（已核对）

- `AlertPopup.addEvent()`：把 `popupAlert.value` 按 `Constants.stringSplitCharacter` 拆成 `eventName` + 可选 `unitId=xxxx`；查 `gameInfo.ruleset.events[eventName]`；`RenderEvent` 用 `event.getMatchingChoices(GameContext(currentPlayerCiv, unit))` 取可选分支，`null` 表示无有效分支（`isValid=false`，原生不渲染）。
- 选中某项时：`choice.triggerChoice(civ, unit)` 触发 uniques，然后 `AlertPopup.close()` 从 `viewingCiv.popupAlerts` 移除该 alert。

### 内核改动

1. 新建 `EventCommands.kt`（沿用现有命令域模式，构造入参 `game / sessionId / revision`）：
   - `pending(alert)`：解析 `popupAlert.value` → `eventName`(+`unitId`)；查 `ruleset.events[eventName]`；用 `getMatchingChoices(GameContext(civ, unit))` 生成 DTO：`{kind:"event", eventName, text:event.text, unitId?, choices:[{index, text:choice.text, enabled, detail}]}`（`detail` 取选项的 civilopedia/unique 说明文本）。
   - `prepare(request)` / `choose(index)`：校验 `index` 落在 matching choices 内 → `choice.triggerChoice(civ, unit)` → `civ.popupAlerts.removeAt(0)`。副作用在 clone 备份保护下执行，失败回滚。
2. `PlayerSnapshot.pending()`：在 `civ.popupAlerts.isNotEmpty()` 分支中，`alert.type == AlertType.Event` 时改为 `add(EventCommands(game).pending(alert))`（`supported=true`），取代当前落到 `else` 的“尚未接入”回退。
3. `GameSession`：新命令名 `eventChoose` 注册到 prepare(78–99)、execute(137–146)、`inPlaceCommands`(303) 三处（本次沿用现有重复模式，注册表化留给第 2 项技术债）；`informationalAlerts` 与 `acknowledge` 语义不动。

### 边界与复刻约束

- 无效事件（`getMatchingChoices==null`）：原生此路径不渲染弹窗。网关侧须先加一条内核测试确认原生下该 `popupAlert` 的真实去留，再决定“移除”还是“保留只读”，务必与原生一致（遵循“复刻原生而非修正 core”的既定决策），且不得引入“随意 dismiss 未接入弹窗”的绕过。
- 幂等：`eventChoose` 走 `requestId + revision` 校验，重复请求返回原结果。

### 前端改动（main.gd）

- 复用现有“事项”页签的 pending 渲染：当 pending 项 `kind=="event"` 时弹出统一事件对话框（标题=`eventName`，正文=`text`，按钮=`choices[].text`，禁用项显示 reason）。
- 选择后发 `eventChoose{index}`，走现有事务锁 / 代际戳 / 确认恢复模式（`_on_busy`、`selection_generation`）。
- 这是“统一事件对话框”的第一个消费者：以后新增需选择的 alert 类型，只要在内核补一个 pending 适配器即可复用同一对话框。

### 测试与验收（红→绿）

1. 新建 `EventFixtures.kt` + `EventCommandsTest.kt`：构造含 `AlertType.Event` 待决弹窗的存档，先写失败用例——pending 暴露结构化 event DTO；`eventChoose` 触发对应 unique 且移除 alert；非法 index / 过期 revision 被拒；无效事件路径与原生一致。
2. `:godot-kernel:test` 全绿 + `installDist`（本项目无 shadowJar）。
3. `smoke.gd` 新增 `event` 场景：真实点击事件对话框选项、断言回合不再被 `PENDING_DECISION` 阻塞、能连续结束回合。
4. `run.ps1 -Smoke` ok=true，双端 error log 0 字节；对同一存档同一操作序列做原生差分（复用 `GameSessionTest` 15 回合差分思路），确认事件处置后状态与原生一致。

### 范围红线

- 不改 `core` 玩法规则；不动 `informationalAlerts` 白名单语义；本任务只做通用事件通道 + `AlertType.Event`，间谍玩法域、完整交易谈判不在本次范围。
